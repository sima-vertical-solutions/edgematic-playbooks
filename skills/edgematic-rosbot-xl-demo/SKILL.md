## ROS and Python environment: fix the previous AI errors

On this Modalix the installed ROS prefix is `/usr/local/ros2`, not an assumed `/opt/ros/humble`. Inspect the board, then use the payload's `setup.sh` from the **deployed NVMe root** in each fresh shell. In Bash, use `set +u` around ROS's generated setup script before restoring `set -u`. Source `/usr/local/ros2/setup.bash` where present; a hard-coded `setup.sh` or login-shell profile is fragile here. On 9 October, a nested launch lost the inherited ROS Python paths: `domain0_feedback_exporter.py` raised `ModuleNotFoundError: No module named 'rclpy'`, and `ros2` raised `PackageNotFoundError: ros2cli`. The board's login profile also emitted `/etc/profile.d/resize-serial.sh: [: too many arguments`; prefer `bash -c` with explicit sourcing over `bash -lc` for nested noninteractive launches.

Append the application and PyNeat paths to the ROS environment; never replace ROS's `PYTHONPATH`, `AMENT_PREFIX_PATH`, or `LD_LIBRARY_PATH` with only the app directory. The current payload sources base ROS, prepends `install/lib/python3.11/site-packages` to `PYTHONPATH`, `install` to `AMENT_PREFIX_PATH`, and `install/lib` to `LD_LIBRARY_PATH`; its run scripts then prepend `/media/nvme/pyneat/lib/python3.11/site-packages`. Before launch, verify `python3 -c 'import rclpy; import importlib.metadata; print(importlib.metadata.version("ros2cli"))'`, `ros2 pkg prefix trailmate_demo1`, and `ldd` of the micro-ROS agent for missing private libraries. `ros2 topic echo` of custom `trailmate_demo1` messages also needs the deployed package Python path. Topic names alone do not prove a subscriber can deserialize them.

## Demo acceptance

- Demo 1 is stationary C270 perception. Check one camera owner, raw/compressed camera, detection and boxed overlay frames, and diagnostics for 60 seconds. Inspect an actual frame and a person-positive overlay. The verified camera was 640x480 MJPEG at 10 FPS. The 13 October post-adjustment Demo 2 window had 601 person-positive detection frames, 600 overlays and a visible green box.
  In the fresh 13 October source build, the camera negotiated 10 FPS but PyNeat inference published about 5 FPS: a 60.09-second Studio-launched board verification received 300 frames each on `/camera/image_raw`, `/camera/image_raw/compressed`, `/detections`, `/detections_overlay`, and `/detections_overlay/compressed`, all person-positive with matched boxed overlay stamps. `wait_for_pipeline_output` timed out because this ROS application exposes topics rather than Insight video channels; verify ROS message rates, types, timestamps and actual boxed content instead of treating that timeout as a failed run. `show_pipeline_output` advertising a bridge does not prove browser rendering, so inspect the Studio viewer separately.
- This ROSBOT XL's legacy firmware uses micro-ROS/XRCE, **not** the current Husarion MAVLink driver. The MCU publishes hidden `/_motors_response` (`JointState`, around 33 Hz), `/_imu/data_raw`, and `/battery_state` on domain 0; `/_motors_cmd` is `Float32MultiArray` in RR, RL, FR, FL order. Use `ros2 topic list --include-hidden-topics -t` (the installed CLI rejects `-a`). The micro-ROS agent needs `XRCE_DOMAIN_ID_OVERRIDE=0`; TrailMate relays odometry and bounded commands between domain 0 and application domain 42. Check fresh named wheel feedback and odometry, not just topic presence. The MCU has emitted invalid nanosecond stamps; use local receipt time for freshness.
  The earlier verified source pins were `micro-ROS-Agent` `af007872b034d1ed31de4815377031350ab0034b` and `micro_ros_msgs` `4594d9db17db735b1e655141fb4afb4cdcfc5789`. Clone those exact revisions through Studio when reproducing this board's agent, rather than cloning floating `humble` copies and then cloning them again. A fresh ARM64 SDK build of the agent includes a large XRCE C++ superbuild; wait for its real completion marker before deploying.
  The 13 October physically verified bridge expected exact JointState names `rr_wheel_joint`, `rl_wheel_joint`, `fr_wheel_joint`, `fl_wheel_joint`, used wheel radius 0.05 m and command turn radius 0.22 m, and mapped `[right,left,right,left]` to the MCU. A later fresh generator incorrectly wrote `front_left_wheel_joint` style names, radius 0.048 m and turn radius 0.135 m before seeing live feedback. Compare new source against these observed values and the current MCU messages; never mark a new conversion verified from assumed URDF geometry alone. The prior attended 0.04 m/s command and 0.05 m/s odometry measurement establish the earlier mapping on this same board, but a changed adapter still needs guarded acceptance.
- Demo 2 starts disarmed. Verify exactly one `/_motors_cmd` publisher and one MCU subscriber, one camera owner, fresh wheel odometry, `base_status.feedback_fresh=true`, `nonzero_commands=0`, and zero requested/measured velocities. On 13 October Studio's guarded run produced 1,990 wheel-odometry samples in 60 seconds at zero measured motion. `base_status` is on domain 0; `/trailmate/follow_status` is on domain 42. Do not send arm or movement keys in unattended checks.
- Open the live overlay in EdgeMatic/Flora and the deployed `tui.sh` through the paired device PTY. The current TUI keys are R reset, L person lock, F follow, M manual, W/A/S/D bounded manual, U disarm, Space latched stop, Q quit. Check the TUI renders, shows disarmed state and fresh feedback; leave physical following and stop demonstration to the attended operator. Do not claim physical motion or a stop distance from idle telemetry. If a Studio build lacks the Robot TUI panel, use its device terminal instead of emitting an unsupported directive.
  During the attended 13 October test, a close-up view of only the operator's legs produced two disjoint person boxes and correctly held zero motion. Moving about 1.5-2 m back gave a single full-body box. The Studio terminal then commanded a short bounded follow: maximum requested forward speed 0.04 m/s, measured wheel speed 0.05 m/s, and measured speed returned to zero about 0.16 s after the latched stop. The controller ended disarmed. Recheck framing before any physical demo and keep the sole-person rule.

For this Linux Studio install, port 8088 was forwarded to the SDK container while the browser device terminal connects directly to sidecars on ports 8761–8770. Forward the full terminal port range to the Studio container before a browser TUI test; a successful `POST /terminal/devices/{id}/session` alone does not prove the browser can reach the returned WebSocket port. The live-output viewer at `/live-output?bridge=ws%3A%2F%2F<board>%3A8765&panels=overlay,raw,detections,odometry` rendered boxed/raw feeds and zero velocity in a browser on 13 October.

The old ROSBOT XL micro-ROS reference in `edgematic-stiga-tui-demo` describes an earlier operator layout; use the current TrailMate scripts and observed graph for this demo.
