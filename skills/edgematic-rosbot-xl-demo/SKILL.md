# TrailMate on ROSBOT XL

Use the active selected Studio project and paired device. Treat addresses below as observations to recheck, not pairing defaults. Keep generic EdgeMatic skills robot agnostic. The 13 October 2026 `.3` run used board `192.168.135.3` (machine-id `7565608e3ebf487a90e352eb7147d777`), laptop Ethernet `192.168.135.2`, MCU `192.168.77.3`, board MCU interface `192.168.77.2`, Studio project root `/workspace`, and application `/workspace/TrailMate`.

## Before the recording

1. Confirm the selected device, SSH host key and machine identity, board reachability, direct MCU ping, NVMe mount, Neat match, and USB C270 by-id path. The observed camera was `/dev/v4l/by-id/usb-046d_C270_HD_WEBCAM_ECC3EC60-video-index0`; the video device number can change. Verify the frame is aimed at a person before claiming boxed detections. On 13 October the first 60-second run had 600 healthy frames but zero persons because the C270 faced the underside of a shelf.
2. After a board reboot, verify its clock. This board has no reliable RTC and reverted to April 2026; set UTC from the host, then verify clock and topic stamps. Check `end0` retained both the direct board address and `192.168.77.2/24`. Keep the laptop's unrelated Wi-Fi/VPN routes intact.
3. On this x86 Linux host, verify ARM64 binfmt and both SDK containers. After host reboot, `ros2-sdk` failed with `exec format error` until binfmt was registered. Use the host's authorized Docker access for repair. The ROS build channel in `ros2-sdk` is a process and dies on container restart even though `/workspace/.edgematic/ros-build-channel.json` remains. Check the process and Studio-to-channel reachability; re-run `/workspace/sima-core/tools/edgematic/provision-build-channel.sh` **inside `ros2-sdk`** when stopped. Do not infer a live channel from the JSON file alone.
   This existing ROS SDK also needed `libwebsocketpp-dev` and `rapidjson-dev` for the packaged Foxglove bridge. They are installed now, but this workspace's `provision-modalix-deps.sh` revision does not list them; verify the headers/packages before a fresh-container build. Studio's build channel only launches build scripts and does not grant arbitrary `apt` access to the compiler container. A prior agent therefore surfaced a host `docker exec` package command. Repair the provisioning source/installer for durable fresh-container automation rather than expecting `run_command` to install packages in `ros2-sdk`.
4. Call `prepare_ros_build` with `script: "build.sh"` for `/workspace/TrailMate`; the parameter is relative to the application. `script: "TrailMate/build.sh"` produced a doubled path. Demand `run_on: "container"`, poll `get_build_status` to terminal `ok`, and inspect the `EDGEMATIC_BUILD_EXIT=0` marker. Studio's `run_command` runs in the Studio/Neat container, not `ros2-sdk`; it cannot replace this channel. `run_on: "host"` means the channel is unavailable. A host Codex session with Docker access can repair it without asking the user to paste a command. Studio alone has no general arbitrary-command API into `ros2-sdk`.
5. If an automatic build fails deleting `payload/` after an earlier manual root build, inspect ownership and return only generated application output (`payload`, `build`, `install`, `log`) to the workspace owner before retrying. The channel correctly drops privileges to that owner. Do not repeatedly run the build as root to conceal an ownership error.
6. Deploy the complete named payload through `deploy_to_device`. In the observed Studio project rooted at `/workspace`, pass `payload: "TrailMate/payload"`; passing only `payload` is an invalid path. Confirm remote root `/media/nvme/applications/TrailMate`, all entry points, model and install tree. A Studio project typed `PYTHON` invokes its entry point with Python: use the staged `run.py` for Demo 1 and `run_demo2.py` for Demo 2. Passing `run.sh` caused a Python `SyntaxError`. The Python wrappers must `exec` the guarded shell launch in foreground so Studio tracks the live process; a detached `setsid` launcher can look finished while children keep running.

## ROS and Python environment: fix the previous AI errors

On this Modalix the installed ROS prefix is `/usr/local/ros2`, not an assumed `/opt/ros/humble`. Inspect the board, then use the payload's `setup.sh` from the **deployed NVMe root** in each fresh shell. In Bash, use `set +u` around ROS's generated setup script before restoring `set -u`. Source `/usr/local/ros2/setup.bash` where present; a hard-coded `setup.sh` or login-shell profile is fragile here. On 9 October, a nested launch lost the inherited ROS Python paths: `domain0_feedback_exporter.py` raised `ModuleNotFoundError: No module named 'rclpy'`, and `ros2` raised `PackageNotFoundError: ros2cli`. The board's login profile also emitted `/etc/profile.d/resize-serial.sh: [: too many arguments`; prefer `bash -c` with explicit sourcing over `bash -lc` for nested noninteractive launches.

Append the application and PyNeat paths to the ROS environment; never replace ROS's `PYTHONPATH`, `AMENT_PREFIX_PATH`, or `LD_LIBRARY_PATH` with only the app directory. The current payload sources base ROS, prepends `install/lib/python3.11/site-packages` to `PYTHONPATH`, `install` to `AMENT_PREFIX_PATH`, and `install/lib` to `LD_LIBRARY_PATH`; its run scripts then prepend `/media/nvme/pyneat/lib/python3.11/site-packages`. Before launch, verify `python3 -c 'import rclpy; import importlib.metadata; print(importlib.metadata.version("ros2cli"))'`, `ros2 pkg prefix trailmate_demo1`, and `ldd` of the micro-ROS agent for missing private libraries. `ros2 topic echo` of custom `trailmate_demo1` messages also needs the deployed package Python path. Topic names alone do not prove a subscriber can deserialize them.

## Demo acceptance

- Demo 1 is stationary C270 perception. Check one camera owner, raw/compressed camera, detection and boxed overlay frames, and diagnostics for 60 seconds. Inspect an actual frame and a person-positive overlay. The verified camera was 640x480 MJPEG at 10 FPS. The 13 October post-adjustment Demo 2 window had 601 person-positive detection frames, 600 overlays and a visible green box.
- This ROSBOT XL's legacy firmware uses micro-ROS/XRCE, **not** the current Husarion MAVLink driver. The MCU publishes hidden `/_motors_response` (`JointState`, around 33 Hz), `/_imu/data_raw`, and `/battery_state` on domain 0; `/_motors_cmd` is `Float32MultiArray` in RR, RL, FR, FL order. Use `ros2 topic list --include-hidden-topics -t` (the installed CLI rejects `-a`). The micro-ROS agent needs `XRCE_DOMAIN_ID_OVERRIDE=0`; TrailMate relays odometry and bounded commands between domain 0 and application domain 42. Check fresh named wheel feedback and odometry, not just topic presence. The MCU has emitted invalid nanosecond stamps; use local receipt time for freshness.
- Demo 2 starts disarmed. Verify exactly one `/_motors_cmd` publisher and one MCU subscriber, one camera owner, fresh wheel odometry, `base_status.feedback_fresh=true`, `nonzero_commands=0`, and zero requested/measured velocities. On 13 October Studio's guarded run produced 1,990 wheel-odometry samples in 60 seconds at zero measured motion. `base_status` is on domain 0; `/trailmate/follow_status` is on domain 42. Do not send arm or movement keys in unattended checks.
- Open the live overlay in EdgeMatic/Flora and the deployed `tui.sh` through the paired device PTY. The current TUI keys are R reset, L person lock, F follow, M manual, W/A/S/D bounded manual, U disarm, Space latched stop, Q quit. Check the TUI renders, shows disarmed state and fresh feedback; leave physical following and stop demonstration to the attended operator. Do not claim physical motion or a stop distance from idle telemetry. If a Studio build lacks the Robot TUI panel, use its device terminal instead of emitting an unsupported directive.

For this Linux Studio install, port 8088 was forwarded to the SDK container while the browser device terminal connects directly to sidecars on ports 8761–8770. Forward the full terminal port range to the Studio container before a browser TUI test; a successful `POST /terminal/devices/{id}/session` alone does not prove the browser can reach the returned WebSocket port. The live-output viewer at `/live-output?bridge=ws%3A%2F%2F<board>%3A8765&panels=overlay,raw,detections,odometry` rendered boxed/raw feeds and zero velocity in a browser on 13 October.

The old ROSBOT XL micro-ROS reference in `edgematic-stiga-tui-demo` describes an earlier operator layout; use the current TrailMate scripts and observed graph for this demo. Preserve successful Studio build/deploy/run IDs, a 60-second topic report, a boxed frame, and any remaining physical acceptance limit in the handoff.
